What the structures tell us

The useful difference is the surrounding machinery.

All three connect model decisions to tool observations and repeat. Their main differences are what the host guarantees, how much context it manages, and how many lifecycles it supervises. More components do not establish better task performance; fewer components do not establish lower end-to-end cost.

04 / proposed · not existing project code

One coding agent. A small inference kernel.

Keep one task state and one tool loop. Route inference calls between models inside that loop.

Implement a thin StateGraph rather than adopting the full terminal application. Reproduce mini-swe-agent's clear feedback mechanics on LangGraph, add a few necessities from the richer harnesses, and make the model gateway the main experimental boundary. The proposed graph has seven executable nodes; local/cloud endpoints and persistence are services, not extra agents.

This matches Stage 1: one repository, one task, one active writer, one local endpoint, and one cloud endpoint. The kernel supports only the graph behavior this agent uses. A general optimizer for arbitrary agent designs can follow once there is evidence that the routing policy helps.

Performance is an evaluation requirement, not an architectural guarantee. Local exploration can add turns and duplicate cloud prefill. Start with a cloud-only baseline, then enable the hybrid policy on the same tasks. Keep a change only when measured quality, cost, and latency meet predeclared targets.

The initial routing policy

Local: a bounded discovery window

Allow local inference only for an explicitly eligible, read-only discovery phase. Advertise search and read_file. Use a small configurable allowance, initially up to three model turns as an experiment setting. A no-tool response ends discovery and passes its observations into the same task state.

Escalate when the phase ends, the local context does not fit, an endpoint/protocol fails within the retry policy, a forbidden mutation is requested, or the discovery allowance is exhausted. Host-observable signals drive this decision; the local model's self-reported confidence is insufficient.

Cloud: implementation and recovery

Use cloud inference for edits, difficult debugging, and final reasoning. Once selected, remain on cloud for the task in the first hybrid policy. This deliberately limits routing complexity and repeated context transfer. Model changes never reset tool policy or grant new authority.

The cloud receives a provider-compatible view of the same task, observed file content, current patch/check evidence, and relevant dialogue. Preserve tool-call/result pairing. Normalize provider-specific content; do not blindly forward another provider's cache or reasoning blocks.

These are proposed starting rules, not a claim that discovery is always easy or that three turns is optimal. Cloud-only and local-only baselines may use each model for the whole task; record that intentional policy difference when interpreting the hybrid experiment.

The few additions worth having immediately

1. A model gateway

One inference contract, two adapters, explicit capability/context limits, bounded inference retries, usage and timing. Keep routing in ordinary code before paying for a learned router.

2. A capability boundary

Typed input, valid call IDs, a policy decision, execution, and a matched result. Use serial effects first. Approval and actual workspace/process confinement remain separate responsibilities.

3. Durable task state

A persistent LangGraph checkpointer plus a small append-only event record. Keep external artifacts and operation outcomes addressable. A checkpoint does not roll back the working tree.

4. A bounded context view

Paginate reads; spool large output to files; count full input against the selected model. Compact completed history only under pressure while retaining task, patch, check evidence, and artifact references.

5. Resource limits

Whole-task step, time, and spend limits; per-tool timeouts and output caps. An estimated reservation reduces overshoot but is not a provider-enforced exact spending guarantee.

6. Evidence-based completion

Use the project's configured checks and current diff. Do not run a second verifier model every turn. Invalidate evidence after relevant mutations and report failures or unavailable checks explicitly.

A normal assistant response without tool calls proposes completion. A deterministic gate checks evidence and either finalizes, requests repair, or records a blocked/unverified outcome. No separate planning, handoff, or finish tool is required for this first graph.

MCP: one adapter, the same invocation path

If a Stage 1 task requires MCP, use an existing client for one explicitly configured server. The kernel owns connect → discover/filter → invoke → close, timeout handling, and conversion into the same tool/result contract. Start with a small read-only catalog. Do not build an MCP implementation, marketplace, dynamic tool-search system, or OAuth manager before the workload requires them. The adapter seam should exist even when the first benchmark runs with no MCP server.

Deliberately deferred

A supervisor, specialist agent tree, autonomous reviewer, background workers, team mailboxes, memory consolidation, skill/plugin discovery, embedding retrieval, LSP integration, graph rewriting, and a terminal client/server product. A small project-instruction file can be loaded once at task start; it does not require a skills platform. Add any deferred feature only against an observed failure or measured bottleneck.

Build contract

A direct mapping to LangGraph

Use a typed state and seven node functions. Conditional edges choose continuation; the inference node calls the selected adapter. Compile with a persistent checkpointer, pass a stable thread identity, and use durable interrupts for approvals. Graph assembly sketch

Illustrative wiring, not a runnable implementation. Node bodies, conditional functions, adapters, state schema, and checkpointer setup must implement the contracts above. Use one routing mechanism per outgoing branch; do not accidentally add an unconditional edge alongside a conflicting dynamic route.

builder = StateGraph(AgentState)
for name, fn in nodes.items():
    builder.add_node(name, fn)

builder.add_edge(START, "prepare")
builder.add_conditional_edges("prepare", after_prepare,
    {"route": "route", "stop": "finalize"})
builder.add_conditional_edges("route", after_route,
    {"call": "infer", "stop": "finalize"})
builder.add_conditional_edges("infer", after_infer,
    {"tools": "guard", "candidate": "verify", "repair": "prepare"})
builder.add_conditional_edges("guard", after_guard,
    {"allowed": "execute", "feedback": "prepare"})
builder.add_conditional_edges("execute", after_execute,
    {"loop": "prepare", "check": "verify"})
builder.add_conditional_edges("verify", after_verify,
    {"continue": "prepare", "checks": "guard", "finish": "finalize"})
builder.add_edge("finalize", END)
graph = builder.compile(checkpointer=persistent_checkpointer)
Small state schema and service boundary

Keep durable state serializable and credentials in runtime-owned services. Do not checkpoint open clients or subprocess objects.

AgentState
  task / acceptance_criteria / workspace_id / config_version
  messages                    # stable IDs; paired calls and results
  phase / selected_model / cloud_sticky / route_reason
  local_discovery_turns / retry_counters
  prepared_view_refs          # reconstructable; full artifacts live outside state
  pending_ops / origin        # model calls or configured host checks
  approvals                   # bind decisions to exact operation/input hashes
  workspace_revision / evidence_refs
  usage / elapsed / limits / status / final_result

Kernel services
  model_gateway       local + cloud adapters, capabilities, retry, usage
  capability_runtime  registry, policy, process owner, optional MCP adapter
  context_store       request view, output artifacts, pressure-triggered rollup
  run_store           checkpoint integration, events, operation ledger

For a small prototype these can be ordinary modules in one process. The boundary is about ownership and contracts, not separate services, daemons, or microservices.

Crash, approval, and model-switch invariants
  • An interrupted node can restart from its beginning. Keep the approval node free of effects before the interrupt; validate the resumed decision against the exact proposed call.
  • Checkpointing does not make shell or MCP mutations exactly once. Record operation identities and outcomes; pause on unknown mutation results rather than automatically replaying them.
  • Changing models retains task identity, instruction priority, workspace, limits, approvals, and observed evidence. It changes the request representation and available model-facing tools only through explicit policy.
  • Every pending model call receives a corresponding result or a deliberate repair record before that transcript is sent to another provider. Host-scheduled checks are typed events/evidence; do not create an unsolicited tool-role message without an assistant call.
  • Preserve current workspace/diff/check evidence across context rollup. Never compact away half of a call/result pair.
  • Any operation that can mutate the workspace invalidates relevant verification. For arbitrary commands, assume mutation unless an enforceable restricted operation proves otherwise; a model's “read-only” label is insufficient.
  • Missing configured checks pass through the same guard and executor, then return directly to verification. The host does not need another model call merely to read a successful exit status. Bound failed-check repair and check rescheduling separately.

Measure before adding machinery

Record task success, cloud spend with a dated pricing basis, local GPU/CPU time, total wall time, per-node latency, token counts, retries, escalation reasons, and final verification. Repeat nondeterministic tasks and report uncertainty. Set the acceptable quality and latency margin before reviewing the hybrid results. A smaller cloud token count alone does not establish a better agent.

Implement the cloud-only graph first. Add the second adapter and explicit switch tests. Then enable the local discovery policy. A local SQLite-backed checkpointer plus artifact/event files is a reasonable initial persistence arrangement; reuse the available integration rather than building another checkpoint engine. Add MCP only for a task that uses it. Profile before introducing a learned router, read parallelism, repo indexing, or another agent.

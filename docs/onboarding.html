The PolyInference vision

Local + cloud.
An OS for agents.

The strongest cloud models deliver great results at a steep price. Local models offer inference without a per-token bill, but usually trade away capability and speed. What if we put them together—and let many agents use them like programs use a computer?

Local + cloud intelligenceAgents as programsShared resources
00 /

Why build PolyInference?

Local and cloud AI are excellent complements. The goal is to make them useful together.

Cloud

More capability. A bigger bill.

State-of-the-art cloud models are the project's choice for the hardest reasoning. Paying for every step can make long-running agents expensive, and remote processing raises privacy questions.

Local

No API bill. Tighter limits.

Local models can use hardware you already own and keep suitable work on your machine. Against the strongest cloud models, they often perform worse; on a gaming PC, inference can also be slow.

There is plenty of interest in local inference for cost and privacy. But local-only has its own limits, just as cloud-only does. Use each where it helps: local models for suitable work, cloud models for harder decisions, alongside tools, files, documentation and MCP services. MCP is a standard way to connect tools and information to AI applications.

Run agents like programs.

One slow model call should not hold up every agent. Design for many agents in progress at once: while one uses a tool, another can use available model capacity. Each running agent is a process sharing local/cloud inference, the filesystem and other services.

Software that connects programs and processes to shared compute and resources has a familiar name: an operating system. That is the idea behind PolyInference's Agent OS, and the reason for the architecture below.

The impact we want

Make useful automation affordable, give users more choice over where work runs, and make several agents practical on the resources they have. We integrate existing models and tools; we are not training a new frontier model.

“Free local inference” means no per-token provider fee; hardware and electricity still cost money. Quality depends on the task and model. Concurrency uses spare capacity; it does not make an individual model call faster.

01 /

Thus, the architecture

Agent programs ask for resources. The OS manages access. Models and tools do the work.

The whiteboard has three main stacks: agent design → Agent OS → inference and tools. A frontend lets people run and inspect them. A future scheduler can decide when work should start.

Current implementation

A coding agent and a small OS.

A LangGraph agent plans, assigns work and reviews changes. The OS runs model/tool requests, applies limits and permissions, and saves execution records. A local UI shows progress. General agents can also use the OS without Git or coding tasks.

Vision / proposed

A broader platform.

Automatic agent adaptation, richer MCP integration, quota-aware scheduling and a polished download-and-run experience remain goals. The default “local” endpoint currently calls remote Haiku as a stand-in; it does not run a model on your GPU.

Agent OS is software running on Linux or macOS, not a replacement for the computer's operating system. Diagrams marked Teaching example explain an idea rather than show a measured run.

02 /

LLMs, in plain language

A model predicts text. An agent uses those predictions, tools and saved state to get something done.

Training builds the model.

Training adjusts billions of numerical values, called weights, using examples. Language models learn to predict what comes next; later training can improve how they follow instructions. PolyInference uses existing models.

Inference runs it.

A tokenizer splits your input into tokens: small text units, not necessarily words. The model processes them, predicts the next token and repeats until it stops or reaches a limit. A convincing answer can still be wrong.

What affects speed and memory?

Prefill means reading the prompt; decode means generating the response. A transformer uses attention to relate tokens. Its KV cache saves intermediate attention data so it can reuse earlier work. More context and simultaneous requests use more memory.

The model's weights also need memory. Quantization stores them with fewer bits, reducing their size with possible quality and speed tradeoffs. The serving engine controls actual GPU memory and batching; PolyInference limits requests using configured capacity.

Context is what the model can see now.

A request may include instructions, the objective, files, tool results and prior messages. It must fit the endpoint's context window, leaving room for an answer:

input tokens + space for output ≤ context limit

A chat can feel persistent because the application carries information forward. The model does not permanently learn your project from a call. The agent chooses saved notes; the OS saves execution records and can prepare a smaller input for one call. Tokens and UTF-8 bytes are different measures; both configured limits matter here.

From a response to an agent

An agent repeats a loop: prepare context → ask a model → validate the response → use an allowed tool → observe the result → decide what to do next. A tool call is a request until the host approves and executes it. Saying “I edited the file” does not edit a file.

LangGraph represents this workflow as nodes, routes and saved checkpoints. Running the graph creates a logical process; a node is not automatically a separate agent, CPU thread or GPU worker.

Three useful distinctions
  • API versus agent harness: a raw model API generates output. A harness such as Codex can use tools, so the host must control its access too.
  • MCP versus tools: MCP connects hosts, clients and servers. A registered tool handler here does not automatically provide a full MCP server lifecycle.
  • Open weights versus local: available weights, licensing and where a model runs are separate questions. “Cloud” does not guarantee correctness; “local” does not guarantee privacy.

Measure quality, time and cost per completed task, including retries. More simultaneous calls may increase total throughput while making each response slower. Temperature changes output variation; it does not establish truth.

The agent owns the workflow. The OS owns safe execution and shared resources. Providers own how models run.

Follow one coding request.

The lecture's “build a 2D Minecraft app” becomes a run with an objective and checks. A senior plans and reviews. Workers handle ready tasks; a dependent task waits until the senior keeps its prerequisite's result.

Workers edit separate full Git worktrees under the selected project's .polyinference/worktrees/. Checking and integration take turns on a shared resource. Only the checked successful candidate joins the integration branch; failed or uncertain work stays private. “Create no branches” means one editor on the current checkout.

A finished process, passing command, published commit and accepted product are different things. Final checks must test the actual objective on the reviewed source.

The OS must work for other agents too.

A research or document agent should be able to call a model, use granted tools and save an artifact without inventing coding tasks or Git commits. The application registers operations and permissions through RuntimePorts; the OS checks them, executes them and saves outcomes. Repeating a settled operation's ID returns its saved result. Different arguments need a new ID.

Three kinds of “memory”

The agent's notes preserve meaning. Execution records preserve what happened. A prepared prompt is the input chosen for one call. Leaving optional history out does not rewrite the original notes. Summarizing it is a separate, potentially lossy action that requires opt-in.

The UI's Memory / context drawer shows saved original/prepared inputs and how they were produced. It does not show hidden reasoning or the model's KV cache.

Where settings belong

Generic OS settings live in src/polyinference/system_settings.py; coding defaults/UI choices in agent/system_settings.py; workflow policy in config.py. Examples put OS preferences under system. Keep objective and check choices in agent fields, and avoid defining the same setting in both old flat and grouped locations.

Keep several agents moving

When one agent finishes a model call and uses a tool, another ready agent can use the freed model capacity.

Concurrency means several jobs are in progress. Parallelism means they run at the same instant. An async coordinator can juggle jobs while a model server separately decides what runs together on the GPU. A “slot” is a capacity limit, not necessarily a physical GPU.

These modes still make real remote calls and incur usage. They simulate pacing/faults, not local GPU performance or true token streaming. Read the simulation guide before interpreting results.

The lecture, condensed

The main ideas and examples from the 22-minute session. Proposals describe the vision, not finished features.

00:00–02:20 · AGENTS AS PROGRAMS

A design becomes a process.

A flowchart describes the agent program; running it on a request creates a process. The 2D Minecraft example gives that process a real output. Agent developers write and test the workflow; the OS does not automatically parallelize its logic.

02:21–05:08 · LOCAL + CLOUD

Match capability to cost.

Use cheaper local inference where it is good enough and cloud reasoning where it helps. Local speed can be a bottleneck. Today routing is configured for each run, and the local-labelled default is remote Haiku. Compare full-task quality and cost.

04:55–05:57 · CHOOSE A STACK

Connect supply and demand.

Agents need resources. Models, Bash, files and MCP services supply them. The OS connects the two. Choose one stack and learn its interfaces before trying to learn everything.

06:19–09:56 · SHARE CAPACITY

Let waiting work move forward.

After a model call finishes, an agent can use Bash while another uses the released model slot. When a tool finishes, its agent can queue for inference again. This is the lecture’s CPU analogy; try the resource example above.

10:07–10:36 · FRONTEND

Give people a useful window.

The frontend is separate from the agent and OS. Here it launches runs, accepts steering and run-level resume requests, and displays saved evidence. Python serves the packaged UI; there is no separate frontend build.

10:37–12:35 · QUOTAS + TIME

Save scarce capacity for urgent work.

Proposed: use remaining cloud quota and reset times to defer less urgent work, perhaps until midnight. The five-hour/weekly examples depend on the account; they are not promised allowances. A complete quota scheduler is future work.

12:43–13:32 · MODEL CHOICE

Trade speed for capability when useful.

Proposed: use a faster local model during busy hours and a slower, stronger one when demand is low. This needs measured quality and safe model switching. Static role bindings do not implement automatic day/night changes.

13:32–14:56 · QUALITY + URGENCY

Keep the two decisions separate.

Proposed: a task may require cloud-level reasoning regardless of urgency; another may permit a cheaper substitute. “Need now” and “need tomorrow” concern timing. Keep the scheduler removable so the OS remains independently testable.

15:01–16:07 · TOO MUCH DEMAND

An extra endpoint could help.

Proposed: send eligible queued work to another, possibly more expensive endpoint. This needs spending limits and permission to move the data. The speaker places it later; today’s endpoint pair is not an automatic overflow pool.

16:19–18:54 · WHY INTEGRATE?

Cost, privacy and useful tools.

The Q&A emphasizes integration rather than training a frontier model. Local preprocessing could remove sensitive content before an approved cloud call, but this must be verified. A lane named local does not prove data stays on the machine.

19:02–19:33 · CONTRIBUTING

Begin by testing.

Pick a stack, coordinate with its contributors and the maintainer, set it up and report reproducible bugs. Research, implementation and testing are all useful contributions.

19:41–22:26 · THE END GOAL

Make the complexity usable.

The Q&A mentions OpenClaw as a personal-agent comparison and describes a download-and-run system combining local and cloud AI. The speaker acknowledges uncertainty about uniqueness. The goal is useful integration, not a verified claim that no similar project exists.

Set up and run

Use Bash on Linux, WSL or macOS, with Python 3.10+ and Git. Native Windows backend execution is not supported.

  1. Read the rules first.

    Read AGENTS.md, the complete FIXES.md and related entries. Use the JSON tree to find your primary guide. For agent/OS work, also read the boundary and current decisions/open gaps.

  2. Install the project.

    On Ubuntu/Debian, install any missing tools:

    Bash · Ubuntu / Debian
    sudo apt update
sudo apt install -y git bash curl python3 python3-venv python3-pip

    Clone the repo, or enter your existing checkout and start at the environment steps:

    Bash · repository setup
    mkdir -p ~/projects
cd ~/projects
git clone https://github.com/demonking-mw/polyinference.git
cd polyinference
python3 -m venv .venv-linux
source .venv-linux/bin/activate
python -m pip install -e '.[test]'
polyinference --help

    In WSL, keep source and state on the Linux filesystem and install providers inside the same distribution. Use Linux paths in the UI. No frontend build is needed. For the tested transitive environment, install requirements.lock before the editable package.

  3. Run offline checks.

    Bash · no provider keys required
    python -m pytest -q
ruff check src tests
python scripts/project_docs.py --check

    These use local fixtures, not provider keys. Report failures and skips honestly. For a small change, start with its focused checks and run required broader checks.

  4. Connect providers for a live run.

    The default uses signed-in Codex for senior/specialist work and Anthropic Haiku for workers. Install Codex in the backend's environment using the login guide, then:

    Bash · same host as the backend
    codex --version
codex login
codex login status

    Enter your Anthropic key without storing its value in command history:

    Bash · enter your own credential
    read -rsp 'Anthropic API key: ' ANTHROPIC_API_KEY
printf '\n'
export ANTHROPIC_API_KEY

    Keep keys outside source. A private ~/.config/polyinference/anthropic.env file is also supported; existing environment values win. Repository .env files are not auto-loaded. Model access depends on your account; use the provider guide for supported configuration. The default Codex login path does not require an OpenAI API key.

  5. Try the greeting fixture.

    Bash · foreground UI server
    polyinference ui

    Open localhost:8765 and keep the default project, objective and check. Start run makes real provider calls. Change greeting("Codex") from Hello Codex to exactly Hello, Codex!. Only greeting.py is writable; its unittest is read-only.

    Watch setup, planning, development, review and final acceptance. Each Start creates fresh state; the UI allows one active test. Keep the terminal open. Closing the tab does not stop work; use Ctrl+C after the run settles.

  6. Inspect what happened.

    Agents shows tasks and phases. OS shows processes, waits and operations. Memory / context compares original/prepared inputs. Inspect the exact attempt, not just the latest result.

    Save run · JSON exports diagnostic evidence; Open snapshot views it offline. This is not a full workspace backup. Costs are estimates, not remaining subscription quota.

    Select a paused run, optionally add instructions and click Resume. The agent handles continuation; the OS prepares supported recovery. Saved work and budgets remain. Unsupported recovery shows a plain failure. Offline snapshots cannot resume.

  7. Move to a small real task.

    Choose an absolute project path, a precise objective and meaningful checks. Preserve existing edits; default integration needs a clean checkout. New/nested directories get a repository at that path. By default, work uses an integration branch from HEAD and private task worktrees; explicit Git instructions take precedence. Nothing is pushed by default.

    The Check field takes a command and arguments, not shell syntax such as && or pipes. Put complex checks in a script. Declare build outputs without hiding source. Use ignored testing/ for disposable projects.

Save a repeatable configuration
Bash · edit the copied example before validating
mkdir -p .polyinference
cp examples/agent.mixed.json .polyinference/agent.json
# Edit repository, objective, grants, checks, endpoints and state_directory.
polyinference validate-config .polyinference/agent.json
polyinference ui --config .polyinference/agent.json

Paths resolve from the config file's parent; write grants use project-relative POSIX paths. Changed settings or incompatible program pins need fresh state; one exact Resume predecessor has a recorded compatibility migration. Do not edit old state to force resume. validate-config checks schema; optional provider probes make real calls.

Read configuration, budgets and the complete settings reference. Ordinary UI defaults start with one worker and one slot per endpoint. Worker count, model slots and context capacity are separate limits.

Rules for every change

Preserve the reasons behind earlier fixes. These rules apply to code, tests and documentation.

01

Keep workflow policy in the agent.

Plans, Git rules, check purpose, reply formats, saved notes and final acceptance belong to the agent. The OS supplies general execution services; a non-coding agent must be able to use them.

02

Respect permissions and user work.

Registering a tool does not grant access. Read access does not grant writes. Role names and .gitignore do not give permission. Protect the root branch, HEAD, index and existing edits. Stop unsafe integration if source changes underneath it; retain failed work for review.

03

Never act on incomplete model output.

Keep partial text, usage and stop details as diagnostics. Even parseable JSON is incomplete if the provider reports a cutoff. Validate tool arguments on the host. Retries need separate recorded attempts and real budgets.

04

Resolve uncertainty before repeating work.

A timeout or disconnect does not prove a remote job stopped. Preserve records, source and capacity ownership, then follow recovery. Do not delete journal entries or blindly resubmit. A file write followed by a database failure can leave an uncertain result.

05

Use the right checks.

Prerequisite checks establish readiness; task checks verify an increment; final checks test the product objective on the reviewed tree. Setup-discovered task checks do not become final checks automatically. Explicit legacy checks retain task/final meaning unless acceptance_checks overrides it. Do not weaken criteria to obtain a pass.

06

Understand the trust boundary.

Trusted commands run with host privileges. Path rules and later scope checks are not a security sandbox; Linux bubblewrap is optional. Keep keys out of source/logs. A local endpoint name does not establish privacy or enforced data-location policy.

07

Preserve saved identities and outcomes.

A settled operation ID returns saved evidence; it must not run the action again. Preserve pinned settings, program identity and prior results across restart. Reinstall required tool handlers/protocols before new work. A diagnostic export is not a runnable backup.

08

Report what the evidence supports.

Separate observations, hypotheses, proposals and verified behavior. Record actual commands, results, skips and limits. Do not claim another contributor’s edits, historical tests or simulated overlap as your verification or a GPU benchmark. Logging failures must not replace the original execution outcome.

Required: AGENTS.md · FIXES.md · boundary guide. Check the U01–U04 guarantee gaps before relying on data-policy enforcement, allocation, process limits or paused-worker residency.

Document every change

A fix or feature is unfinished until its related documentation is current—in the same task.

Follow the documentation map.

docs/file-tree.json is the authored inventory. Each feature leaf has one primary Markdown doc and an explicit list of related files. Every first-party code file needs a named responsibility in its primary guide.

Update JSON when files/features appear, move or disappear. file-tree.html is generated: never edit it by hand. This onboarding HTML is authored separately and owned by dev-readme.md.

Update everything the change affects.

  • The primary module guide: behavior, file roles, interfaces and rules.
  • Setup, usage, configuration/defaults, architecture, design and issue documents.
  • Navigation and examples when paths, features or settings change.
  • Review adjacent guides; state which need no edit and why.

Keep new overview/module Markdown guides around 80 lines, with focused pages for detail. Preserve historical specs, graphs and evidence at stable links; mark superseded decisions clearly. Ignore transient state, credentials, environments and build output. Upstream references have separate documented ownership.

Append a FIX entry for each independent change.

Use the live FIXES.md template: next unused FIX-NNNN, local ISO date, title, truthful status and an index row. Include all five parts:

Preserve earlier entries. Add explicit corrections/superseding decisions rather than rewriting history. For a recurrence, link the old fix and explain why it escaped earlier coverage. A useful bug report includes

  • Revision, environment, exact command/launch inputs, objective and effective configuration.
  • Expected/actual behavior, sanitized errors, run/process/operation IDs and whether execution stopped or remains uncertain.
  • A reproduction or saved snapshot plus the relevant source state; keep private work distinct from accepted work.
  • Checks actually run, results/skips and limits; label unverified explanations. Exclude secrets.

A small glossary

The terms you need to read the code and ask useful questions.

15 terms

Agent
A program that uses models, tools and saved state to pursue an objective.
Agent OS
The shared runtime for processes, permissions, resources and execution records.
Inference
Running a trained model on an input.
Token / context
A token is a small text unit. Context is the limited input/history available to a model call.
Prefill / decode
Reading the prompt, then generating the response.
KV cache
Intermediate attention data reused during generation; not the agent’s saved notes.
Endpoint / lane
A configured model connection. The name local does not prove where it runs.
Process
A running agent instance; not necessarily a separate operating-system PID.
Concurrency
Several jobs in progress, sharing resources as capacity becomes available.
Admission
The OS decision that a request has permission and enough capacity to run.
Capability / grant
An available operation, and explicit permission to use it.
Replay / retry
Replay returns a saved result. Retry makes a new, separately recorded attempt.
Unknown execution
We do not yet know whether an operation ended or what it changed.
Acceptance
Evidence that the actual objective holds on the reviewed result.
Snapshot / checkpoint
A diagnostic export versus saved workflow continuation state. Neither is a full workspace backup.
Two model slots, one busy worker: is the OS broken?

Not necessarily. Check ready tasks, worker limits, Git policy, model reservations and tool/check waits. Spare capacity does not create work.

The build passed. Is the product done?

Only if meaningful final checks establish the objective on the reviewed source. Compilation alone may not test gameplay, saving or loading.

A remote job timed out. Can I retry?

First establish whether it stopped and what it changed. Preserve the original records and source, then follow the documented recovery path.

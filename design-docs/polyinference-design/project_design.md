# Polyinference OS: project design

Current implementation scope: [simplified OS](../simplified-os/README.md), paired with the [LangGraph agent](../langgraph-agent/README.md). This document is retained as the broader research proposal. The latest design supersedes its one-worker/one-decode and full-development-copy defaults; use the [source consolidation](../simplified-os/SOURCES.md) for precedence and the five-lecture mapping.

Research/design specification · revised 2026-10-16 using your clarifications and private-copy/two-mutex concurrency model · no OS implementation or benchmark results.

Build the OS as a small, persistent runtime between your LangGraph agent and the local/cloud inference and tool backends. Preserve the agent's cloud-led sprint planning, bounded local coding, programmatic orchestration, evidence checks, and commit/report cycle. The OS supplies process control, backend adaptation, resource admission, shared-state services, and recovery. Its first useful version runs one instance of this application with one coding attempt at a time; increasing process count must not require duplicating model weights or redesigning its request contract.

The uploaded HTML is **the agent design**, including the parts delegated to the LLM OS. It contains **two embedded graph datasets**, not just the visible execution diagram: 15 nodes/19 arrows in the main graph and 19 nodes/19 arrows in the Data & memory model. The latter contains the cloud conductor, immediate memory, trap frames, deferred key frames, pressure-aware reassignment, user steering, and documentation batching. All are accounted for below.

### Clarified invariants

- The LLM OS is an ordinary application-level program operating LLM endpoints and agent/tool services. Its “kernel,” “processes,” scheduling and trap frames are application abstractions. No Linux-kernel integration, system calls, physical CPU scheduling, privileged mode, or host-OS protection subsystem is part of this project.
- Every local process completes as `execution=completed`, `resolution=unresolved`, with assessment verdict `fail`, `uncertain`, or `successful`. Only the sprint coordinator subsequently resolves it.
- The final one or few local-model loop iterations are always testing/examination/assessment. That phase produces the verdict from checks and observations. An earlier implementation-loop claim is not the verdict.
- Every in-progress coding agent owns a codebase copy at a recorded base. Private development overlaps; every shell command uses one global `shell_mutex`. A separate `verification_gate` serializes latest-head merge, at least one reconciliation-development loop, final assessment, commit and shared publication. The coordinator remains active throughout.
- Each agent completion identifies its Git commit so senior review can undo the unit and examine affected/dependent work.
- Steering is recorded immediately but applied only after the local agents already in progress finish. Pending queue items do not need to finish and must not start while waiting for that steering review.

### What the OS must run

The cloud senior is invoked first, then at sprint boundaries or concrete exceptions. It proposes plans, reviews unresolved work, may perform an explicitly assigned specialist task, and proposes completion. Ordinary local execution performs implementation and tests, not just reconnaissance. Repairs normally keep the assigned role; a pressure-policy decision must be recorded separately. Queue exhaustion triggers review, not success. Successful project completion requires both a senior completion decision and current project checks on the reviewed project revision.

A sprint is a coordination interval, not a weekly timer. Its boundary may be queue exhaustion/stall, enough unresolved outcomes, a bounded worker issue, changed assumptions, regression, or user steering. The exact unresolved threshold and progress rule are policies to choose, not facts supplied by the graph.

## 3. Runtime architecture and minimum boundary

Use one application-level LLM OS coordinator. Its runtime kernel schedules logical agent work and calls LLM/tool endpoints through ordinary program interfaces. It does not manage the computer's operating system or enter privileged kernel space. Local/cloud endpoints provide heterogeneous reasoning capacity: they differ in context, tool environment, latency, cost, quality, cancellation and resumability.

Keep six small internal modules behind one typed SDK boundary:

1. **Process/continuation manager:** registered program roles, state, grants, graph driver ownership, spawn/wait/pause/cancel and trap frames.
2. **Admission/scheduler:** worker residency, local decode slots, tool memory/CPU, provider quotas/spend, bounded queues and priorities.
3. **Backend/tool supervisor:** local inference, cloud conductor/adapters, guarded commands, optional MCP lifecycle and external-operation reconciliation.
4. **Project-state service:** task ledger, plan revisions, steering, immediate-memory records and documentation backlog.
5. **Code/evidence service:** private workspace ownership, shell/verification admission, project revision identities, per-agent Git commits, assessment evidence, unresolved reports, senior keep/revert decisions and project acceptance.
6. **Persistent journal/artifacts:** small transactional metadata, a persistent LangGraph saver, immutable Git/file artifacts and bounded event delivery.

These modules can share one Python application. Tool execution is an application integration point. V1 coordinates coding/shell activity through its own critical-section protocol; it does not design Linux sandboxing, cgroups, kernel scheduling or protection mechanisms. Deployment hardening is outside this design. Program-level request limits, tool scope, result attribution and ownership remain LLM OS responsibilities.

Start with application-local SQLite metadata and a persistent LangGraph saver, with explicit separate consistency domains. SQLite WAL is suitable for a single coordinator on local storage; it does not provide multiple simultaneous writers or an external-provider transaction. Store large trajectories, logs, docs and patches as artifacts, referenced from compact graph state. [W1, W6]

The LangGraph subset initially comprises sequential nodes, conditional edges, bounded cycles, asynchronous operation waits and persistent continuation. Start one driver per logical process, with one advancing node at a time. No general dynamic subagents, distributed scheduler, vector database, learned router, native spinlocks, or support for a candidate harness's entire feature set is required. Mini-SWE-agent/Deep Agents remain behavioral/framework references; this task does not select or port them. [W10]

## 4. Execution units and data contracts

### 4.1 Distinct identities

| Record | Meaning and retained identity |
| --- | --- |
| `ProjectRun` | Objective/criteria refs, project grant, plan/working revisions, run limits, policy/catalog versions, steering/control epoch and outcome. |
| `AgentProgram` | Registered LangGraph entries, graph/state/action schema versions and exact kernel capabilities required. |
| `Process` | One controller, cloud strategy/review query, or coding attempt. Owns continuation, grants, wait reason, accounting and outstanding effects. Cloud specialist coding is a coding process using a cloud execution binding; do not create two owners of the same attempt. |
| `TaskSpec` | Immutable revision of a worker task; excludes strategy/orchestration requests. |
| `TaskAttempt` | One effort against that spec/base, with its own process/workspace/report. |
| `Operation` | One intended external effect, such as a model generation, agent turn/job, tool action or commit. Provider retries are separate transport attempts. |
| `DispatchBinding` | Allowed role/backend choice and version for this dispatch; distinct from the immutable run backend catalog and from the TaskSpec objective. |
| `Continuation` | LangGraph thread/namespace/checkpoint and logical step, distinct from host threads, provider sessions and model KV state. |
| `ProviderSession/Job` | Adapter-specific IDs and evidence of external execution; never an authority token by itself. |

G0 has one controller and at most one worker coding attempt at a time, local or cloud specialist. A short-lived strategy query is a logical process as your Cloud Query Processor requests; it need not be an autonomous coding agent or a separate computer-OS process. G1 instantiates more coding processes while retaining one coordinator and shared serving services.

### 4.2 Process/request structures

The PCB needs identity/parent/program versions, input references, state/revision, control epoch, wait target, continuation ref, workspace/grant, finite limits, resource ownership, pending operation IDs, cancellation intent, cleanup/uncertainty and retained result. Model text cannot overwrite any of these authority fields.

Every request envelope carries `schema_version`, authenticated project/process identity, stable `operation_id` and logical-step identity, kind/payload refs, expected state revision/control epoch, grant, deadline, dispatch-binding version, resource vector and trace parent. A fingerprint detects changed intent under the same ID. Large inputs stay as handles. A receipt returns admission state/operation identity; the terminal result identifies actual backend/model, typed status/error, artifacts, usage and termination certainty.

Minimum SDK operations are process create/status/wait/pause/resume/cancel; cloud/local submit and operation wait/cancel/reconcile; shell-mutex and verification-gate entry/release; scoped tool call; artifact read/write; task publish/claim/report/resolve; memory/steering append; documentation enqueue/ack; agent commit and senior-authorized keep/revert. These are conceptual contracts, not a requirement to expose a network RPC service in G0. Combine helpers for convenience without bypassing enforcement.

### 4.3 Worker task and cloud process inputs

| Structure | Required contents |
| --- | --- |
| `TaskSpec` | Kernel IDs and spec/plan versions; objective; change scope; dependency IDs and accepted result refs; concrete base SHA; pinned docs/notes/context refs; allowed/required tools; acceptance criteria ref; eligible execution roles/backends and minimum capability; priority/deadline; step/repair/time/token/spend/output bounds; report version. |
| `CloudProcessSpec` | Mode `initial / sprint_review / plan_correction / specialist / completion_review / doc_update`; objective/task identity; bounded context/evidence refs; expected output schema; required execution kind and tool environment; allowed providers/fallback policy; quota class/priority; finite limits; return target. |
| `TaskReport` | Task/spec/attempt/process IDs; plan/control/binding versions; `execution=completed`; `resolution=unresolved`; assessment `verdict=fail / uncertain / successful`; assessment phase/iteration refs and reasons; test/examination evidence with revision; base/commit SHA and changed scope; actual usage; stop reason, change summary and hazards. Stop reason is not a fourth verdict. |
| `PressureSnapshot` | Account/provider/bucket scope; observation time/staleness; capacity/quota fields actually available; reset/retry hints; known pending reservations; uncertainty; health; queue age; policy version. |

The task's `base_sha` becomes concrete before execution. Dependency completion can materialize a new executable spec revision; workers never start from a moving `latest`. A cloud plan is validated for schema, grant subsets, finite bounds, queue size and acyclic dependencies before atomic publication. A claimed task reserves worker residency, not every backend resource it may ever need.

## 5. Control protocols

### 5.1 Normal run, final assessment, and senior resolution

1. Persist objective, criteria, program configuration and limits. The first inference invokes the cloud senior; its validated sprint populates the worker-task queue. Cloud planning/orchestration requests remain separate from that queue.
2. Claim a ready task and initialize its logical process with its own codebase copy at base `B`. Develop privately in parallel with other processes; non-shell private edits need no global editing permit. Every shell/script command individually acquires the global shell mutex, including Git/test commands invoked through shell.
3. Run bounded implementation iterations: local model → proposed action → tools → observation → result processing → local model. A completion claim, known failure, inability to justify progress, or implementation allowance ending requests the reconciliation/final-assessment phase. Reserve its allowance before implementation starts.
4. Release any outside shell ownership before requesting `verification_gate`. After entry, capture latest provisional shared head `H`, preserve the private delta and merge `H` into this copy. Run at least one development loop with a special reconciliation prompt to examine incoming changes and necessary adaptations, even after a clean merge. Keep the gate through further repair, final assessment, commit and publication. **The final one or few local LLM iterations are testing/examination/assessment.** They use assessment-mode prompts and the existing inference/tool/observation path. Run relevant tests, examine code and outputs, and assess evidence for the exact revision. Automated check records are inputs, not a replacement for these last loop iterations. An implementation repair returns to implementation and must be followed by a new final assessment.
5. The assessment produces exactly one verdict: `successful` when the evidence justifies success; `uncertain` when success cannot be justified or something remains questionable; `fail` when something definitely went wrong and could not be fixed. A green command alone need not justify successful. Missing/inconclusive tests usually support uncertain; a definite unrepaired defect supports fail. A timeout/budget exhaustion is recorded separately and is not automatically a fourth verdict or proof of failure.
6. Commit the agent's identifiable code change as its undo unit, record the actual SHA and assessment evidence, then publish `execution=completed, resolution=unresolved` for **every** verdict. The completed process need not remain executing: its unresolved record stays in the queue until senior review. Publish the new provisional head with the unresolved report before releasing verification ownership; release shell ownership after each command, not for the whole verification phase. A no-diff attempt may use an empty metadata commit; a crash or unknown commit outcome is interrupted, not fabricated completion.
7. The sprint coordinator reviews all completed processes, including successful ones. It resolves them by retaining work, reverting its commit, requesting another attempt, or deferring with reasons. Reverting still requires blast-radius analysis and suitable checks (§6.3). The assessment verdict is retained as historical evidence; the coordinator's resolution is a separate decision.
8. Dependent tasks wait for the required senior disposition. In provisional shared history, published code is present before senior review; that does not mean it has been approved. Queue exhaustion or a blocked dependency frontier requests review. A project completion proposal still requires project-level examination of the reviewed revision.

```text
phase: private development -> acquire verification -> merge latest head
       -> reconciliation development (at least one loop)
       -> testing/examination/assessment -> commit + publish -> release verification
       ^                          |
       +------ repair needed -----+   (follow repair with another final assessment)

execution: pending -> in_progress -> completed
resolution on every completion: unresolved -> reviewed/resolved by sprint coordinator
assessment verdict: fail | uncertain | successful
stop_reason: optional, separate (for example budget_exhausted or unavailable_test)
review action: keep | revert | retry | defer
```

Completion of execution and resolution are deliberately independent. An interrupted/cancelled process has a lifecycle record and retained work; it is not made successful or assigned a made-up assessment verdict. If the mandatory final assessment cannot run, keep the process interrupted/assessment-pending rather than claiming normal completion.

### 5.2 Cloud conductor: real protocols, shared limits

Declare each backend as `model_inference` or `agent_job`. For raw inference, the OS supplies the bounded action/observation loop when a cloud task needs tools. A one-response structured planning invocation can remain one inference operation. For an agent endpoint, the adapter manages its native session/turn/job lifecycle, tool environment, event stream and completion. Do not wrap an autonomous tool-using harness in another competing tool loop. [W2]

The normalized output is a typed plan/review/completion proposal or a specialist candidate with retrievable evidence. A provider job that hides required tool observations or cannot constrain scope is not a compatible substitute for a guarded specialist process. Start it in an explicitly scoped agent/tool environment and return identifiable changes and evidence; if the adapter cannot meet that contract, exclude that execution mode.

Track **separately** account subscription windows/credits, API request/token rates, maximum active calls, project spend and reserved future review capacity. Five-hour/weekly/monthly windows in the HTML are examples, not universal constants. Codex exposes rate-limit snapshots/notifications; fields can be missing and source versions can differ. The OS must preserve observation time and unknown values, not invent exact remaining tokens from a percentage. Claude API rate limits and spend limits have distinct reporting/retry behavior. [W2, W3]

All OS-managed processes sharing an account draw from one ledger. Other applications can also consume that account: the OS cannot guarantee an exclusive provider quota reservation unless the provider supports one. It can reserve its own admission allowance conservatively and react to authoritative rejection. Keep local ledger reservations distinct from provider-reported totals to avoid counting the same usage twice.

Overflow uses only preauthorized compatible destinations and the task's fallback/spend/data policy. Pin one mutable conversation operation at a time. A quota refusal known to occur before execution can wait or choose a compatible fallback; a disconnected submitted job must be reconciled before any replacement. Predicted reset time schedules a refresh, not proof that capacity returned. Reserve enough allowed capacity for necessary planning/review where measurable; when that cannot be guaranteed, expose the risk and pause truthfully.

### 5.3 Pressure-aware scheduling and reassignment

Your conductor reports pressure; the orchestrator decides what to stall/release and whether to request a different allocation of work. The kernel validates each decision. Treat pressure as several signals—local memory/decode pressure, provider availability, account-window headroom, spend, queue age and critical path—rather than one CPU-load number.

Use task priority plus aging and dependency criticality; restrict low-pressure background work to user-authorized queued objectives. A subscription with low marginal cost still has opportunity cost, finite quota and possible quality differences. Never manufacture background tasks just to consume a subscription.

| State of the work | Permitted action |
| --- | --- |
| Pending, no active effects | Stall/release or choose an eligible binding; atomically update binding version and retain queue age/history. |
| Between settled model/tool operations | Save a safe continuation; pause. Resume with the same binding, or apply an authorized compatible rebind with a new binding epoch and refreshed context. |
| Active decode or known external agent turn | Request supported cancellation/drain or let it finish. Keep its resources attributed. A “stall” flag alone neither stops generation nor releases quota. |
| Active command/unknown mutation outcome | Contain/reconcile and inspect workspace before any reassignment. Do not start a second writer. |
| Incompatible model/harness state, new scope or changed criteria | Close/checkpoint where possible, then create a linked new attempt/spec. Transfer artifacts, not hidden agent internals. |

The task contract declares eligible bindings and a minimum capability/quality policy; pressure cannot expand authority or silently weaken acceptance checks. Strategic work stays cloud unless explicitly defined as local-eligible. A worker repair keeps its assignment unless a recorded policy decision changes it at a safe point. Add hysteresis/minimum residence or a finite rebind limit so fluctuating quota signals do not cause repeated context rebuilding. Numerical thresholds need measurement.

G0 implements pause/release and pending-task rebinds. Running-task pressure changes initially drain to a safe point or finish the attempt; seamless cross-harness migration is an explicit later capability. This still handles tasks already released into the system without promising arbitrary-instruction preemption.

### 5.4 User steering: finish the currently running local agents, then plan

Record steering immediately in the ordered inbox, but do not apply it to current agents' goals, prompts or task specifications. At receipt, serialize with task dispatch and capture `drain_set = {local process IDs currently in_progress}`. “In progress” includes a started agent waiting for inference, a tool or either the shell mutex or verification gate; it does not mean only an agent generating tokens at that instant. Pending, unstarted queue items are **not** in this set.

Stop starting further local agents while steering waits. Every process in the captured set continues its existing implementation, mandatory final assessment, Git commit and unresolved-report sequence. Its operations remain admitted under its existing task contract. Do not pause, cancel or change its assignment merely because steering arrived. Do not wait for the rest of the task queue to finish. If the set is empty, the planner can be scheduled immediately.

Once every captured local process has completed and its report is stored, invoke the sprint planner/coordinator with the pending steering and those results. Only this planning step interprets/applies steering, resolves completed outputs, and revises/replaces/cancels pending work. Publish the new plan and acknowledge the exact consumed input range, then allow dispatch again. A successful local assessment still remains unresolved until this review.

An input sequence and dispatch gate are bookkeeping for this delayed application, not an immediate semantic replan. Increment `steering_sequence` on receipt; advance the accepted `plan_revision` only when the planner publishes its decision. Receipt does not invalidate running agents' existing plan or prevent their unresolved reports. Earlier references to control epochs mean lifecycle/publication version checks, not permission to apply steering early. New steering received while draining joins the pending input range; no new local agents start. Steering arriving during an already-running planner stays pending for the next serialized review unless that invocation explicitly incorporates it. The OS must not lose it or silently rewrite the planner's input.

If an active agent is stuck or interrupted, report the blocker rather than pretending it finished. A separate explicit emergency stop/cancel is a different user action. Quota waits affect when planning can run; status and bookkeeping remain available throughout. An already-running cloud request is reconciled/serialized as needed but is not added to the captured local drain set, and steering receipt itself does not rewrite its accepted plan.

### 5.5 Immediate memory and documentation batching

“Unified” means project-scoped service, not one mutable text blob. Use distinct records for original objective, ordered steering, versioned senior notes, task hazard notices, report/change inbox and doc revisions. A hazard names attempt/base/commit, affected scope, uncertainty and resolution state. It is advisory context; dependency/review rules, private workspace ownership and the two mutex protocols enforce sequencing. A hazard must say whether the failed/uncertain commit is already present in the shared project history or isolated elsewhere. In v1, it can already affect the current tree before review; warn on that actual revision and scope.

Workers pin a bounded memory/doc snapshot on task start. Urgent new hazards can request a pause/review; do not silently rewrite an in-flight prompt history. Senior notes are proposals until host publication. Summaries retain provenance and never replace authoritative test results or permissions.

Every report and final queue disposition enqueues one uniquely keyed history/change event, including cancellations. Documentation stores the backlog durably, even if no model update has run. At the configured batch threshold or sprint review, capture a cursor/range and accepted code revision. If text generation is needed, create an ordinary bounded doc-update task using the same local harness and resources; do not let Documentation write directly into an active worker checkout. Publish the new doc version and advance the consumed cursor together, conditional on the captured inputs. Concurrent new reports remain queued. Failed updates retain their backlog; replay cannot double-apply a range.

The threshold is a tuning choice; the architectural question is whether a sprint must wait for fresh docs or can start with a known older doc version plus the unprocessed delta. Pick and record that policy (§13). Do not make a doc task depend on consuming its own future report, creating an infinite update cycle.

## 6. Scheduling, memory, critical sections and Git undo

### 6.1 Schedule real resources

Separate worker-task eligibility, process-ready state and operation admission. A logical process waiting on inference need not block the application control loop, while its backend request and resident state still consume resources. LangGraph's per-invocation concurrency settings are not a global provider/memory scheduler. An asynchronous controller waiting for children must release transient execution capacity needed by those children. [W4, W5]

G0 may initially admit one coding process and one local decode, but uses the same private-copy/two-mutex contract as the multi-agent version. G1 admits several private development processes. Exactly one shell operation runs at a time, and exactly one process occupies the reconciliation/verification/commit/publication phase. These capacities are independent of resident-agent count and local decode count. Provider-session turns remain serialized within each mutable session.

Admission reserves the entire simultaneous resource vector atomically or none: local decode capacity, domain-specific memory, concurrent tool-call allowances, startup requirements, provider allowances and grant/deadline. A claimed worker does not hold a decode permit while waiting for tool memory. When a stage ends, release only resources it actually ceased using. Long-lived model/MCP residency is separately owned. These are application admission decisions, not physical CPU scheduling.

For each physical memory domain `d`:

```text
shared_model_residency[d] + additional_active_inference_peak[d]
 + kernel_and_resident_process_peak[d] + tool/MCP_residency_and_call_peak[d]
 + bounded_buffers_not_already_counted[d] + headroom[d]
 <= usable_capacity[d]
```

Keep machine RAM, discrete VRAM and truly unified memory estimates separate, without double-counting. Prompt/KV footprint varies with context/batching. The application admits work against measured/backend-reported capacities; it does not implement computer-OS memory enforcement or claim a hard physical bound from an estimate. The supplied plan gives no hardware/model sizes, so numeric capacity claims would be invented.

Prefer retaining the local model. Keep tool schemas compact, histories/output offloaded and active driver count bounded. MCP is optional if direct tools suffice. For a needed server, reserve startup peak, start exactly one instance per generation, initialize/negotiate before READY, and acquire call leases before use. Zero-lease idle instances may be reclaimed; release residency only after confirmed exit. An impossible model+tool fit becomes `BLOCKED_RESOURCE_CONFIGURATION`, not an endless restart/reload loop. [W8]

Within eligible queues use priority classes with age/finite overtaking. When a compatible large request has been bypassed too often, stop admitting new conflicting work, drain existing bounded users, then grant its whole vector. Keep control/reconciliation memory and delivery capacity available. Backoff respects provider retry hints; permanent spend stops are not ordinary short rate-limit retries. [W3]

### 6.2 Parallel private development and two critical sections

The complete contract and failure scenarios are in [Concurrent coding protocol](concurrent_coding_protocol.md). Each in-progress process owns a codebase copy at a recorded base `B`. Full working trees are the initial default. Partial copies require sufficient dependency/build/test closure and a mapping back to the full project; otherwise their assessments cannot justify a full-project publication.

| Ownership object | Protected work | Release boundary |
| --- | --- | --- |
| `shell_mutex` | Every shell/script command across managed processes, even in different copies; includes Git/build/test commands executed through shell. | Relevant operation and background effects actually finished, results accounted for. |
| `verification_gate` | Capture shared head, merge it into private work, reconciliation development loop(s), final assessment, commit and shared publication. | New head/report publication is durable, or an explicit abort is reconciled without normal completion. |

Private reasoning and non-shell edits occur outside these critical sections. Waiting agents can continue private development until they choose to queue their final candidate. All tool requests name their workspace; shared services/caches/remote effects need explicit scoping or conflict rules. A copy is not evidence that every external effect is isolated.

**Lock order is `verification_gate -> shell_mutex`.** An agent executing shell outside verification releases shell ownership before waiting for verification. Inside verification, acquire/release shell individually for each command; do not reserve it throughout model reasoning. FIFO/age-aware admission gives waiting verifiers and other shell users progress. Keep short coordinator locks/transactions separate from both long-lived permits. The LLM OS kernel remains an active application event loop; no computer-kernel preemption is required.

```text
Agent A: private dev -> acquire verification -> merge latest H -> reconciliation dev
          -> final assessment -> commit P1 -> publish head/report -> release
Agent B: private dev ............ wait ........ -> acquire -> merge P1 -> reconciliation dev
          -> final assessment -> commit P2 -> publish head/report -> release
Shell:   one operation at a time; acquire/release individually, including inside verification
```

At least one specially prompted development loop after merging is mandatory, even if Git reports no conflict. Further repairs are bounded; final testing/examination/assessment follows the last repair. Reserve phase allowances. A process cannot exit normally just because one reconciliation loop ran: it needs its assessment, real commit and publication boundary. Unknown tool activity keeps applicable exclusion; a timeout alone does not unlock a still-mutating operation.

Persist both owner tokens, wait positions, process phase, pending operation IDs, captured head, workspace revision and publication status. On crash, reconcile effects and publication before granting a replacement or allowing the old owner to resume. A verifier cannot hold its gate while waiting for another agent to enter it or waiting for senior review that needs a revert under the same gate. Complete/release first, then review.

### 6.3 Provisional shared head, unresolved results and Git undo

**Publication policy selected to match your sequence:** every normally completed process publishes its assessed commit to the provisional shared history, including `fail` and `uncertain`, with its hazards. Every report remains unresolved until sprint-coordinator review. A subsequent agent receives that head and its unresolved provenance. Dependency/hazard policy can require senior review before affected work proceeds. Keeping questionable commits private is an explicit alternative that changes this handoff; it is not silently substituted here.

Record original base `B`, private pre-merge delta/history, captured shared head `H`, final assessed tree/evidence/environment, resulting commit `P`, verdict and changed scope. Prefer one attributable published task commit whose parent is `H`: it contains this process's net delta and conflict adaptations, not the incoming changes already in `H`. Retain private merge/WIP history as evidence. This makes the senior's revert undo this agent's contribution without also undoing its predecessors. Publishing merge commits instead requires an explicit mainline/revert contract.

Hold `verification_gate` through publication. First ensure immutable Git/evidence objects exist; then a short metadata transaction compares expected head/plan authority, publishes `provisional_head=P`, the immutable completed-unresolved report and notification intent. A convenience Git ref is a projection of that authority and is reconciled after restart. This is not one transaction across Git, LangGraph and providers. A process-local commit without shared publication is not enough: the next process must capture the newly published head.

Senior review keeps/reverts/retries/defers independently of the local verdict. A revert acquires the same verification gate, uses shell ownership for commands, examines later/dependent commits and blast radius, records an explicit revert commit and checks, and publishes the resulting head before release. Preserve original assessment and review history. Git avoids reconstructing inverse edits; it cannot reverse non-Git effects or prove downstream correctness.

The final project decision uses the reviewed resulting revision, not just the provisional head or a green task assessment. This preserves your unresolved-until-review semantics while allowing agents to build sequentially on one another's published code.

## 7. Trap frames, interruption and recovery

A trap frame is a durable **resume manifest**: process/program/state versions, current graph checkpoint and next logical step, task/spec/plan/control/binding versions, workspace/base/tree, trajectory/artifact refs, counters/remaining limits, pending operations/provider IDs, reservations, docs/memory versions, report/doc cursors and pause reason. Shared queue/memory/docs are referenced by durable versions; do not copy the whole project into every frame.

Ordinary stalling lets the active bounded operation or task finish, then saves at a supported boundary. Resume revalidates grants, current control/plan state, compatible code/schema/binding, workspace integrity and outstanding effects before dispatch. A frame cannot serialize hidden chain-of-thought, a native provider stack, sockets or local model KV state. A provider session is resumed only if its adapter supports it; otherwise rebuild from retained artifacts or start a linked attempt.

LangGraph checkpoints persist graph state; interrupt resumption can replay the node from its beginning. Use a persistent saver with synchronous checkpoint durability initially and small submit/consume boundaries. The kernel must also persist the logical-step→operation mapping before sending, because the process may crash after submission but before its graph checkpoint records the receipt. [W1]

```text
operation: PREPARED -> SUBMITTING -> ACTIVE -> terminal
                                  \-> UNCERTAIN -> reconciled outcome
```

Only PREPARED is known not to have submitted. After SUBMITTING, a lost reply may mean execution happened. Reattach/query by supported ID or inspect known side effects; never blindly replay an unknown mutating action or agent job. Preserve applicable reservations and a visible supervisor until outcome/termination is established. A timeout/cancellation request does not prove the remote job or command descendants stopped. [W2, W4, W9]

Startup recovery loads metadata, verifies referenced checkpoints/artifacts, reconciles known/uncertain operations, repairs pending notifications/projections, then resumes eligible processes one owner at a time. Unknown mutations block conflicting code/shell entry and final acceptance. Report/commit reconciliation uses task/attempt identity and actual Git state. A minimal durable journal is required for these guarantees even while the HTML's broader **Key frame** feature remains deferred.

A later key frame should be a consistent-cut manifest of queue/plan/head/steering/doc cursors, continuation refs and operation journal positions. Quiesce or use a defined capture protocol, retain all referenced objects, and reconcile external work on restore. It is not a bit-for-bit snapshot that reverses API billing or remote effects. Full power-loss guarantees and distributed failover remain research questions.

## 12. Design choices that materially steer the project

Each option is viable under a stated target. Recommendations choose an initial path, not a claim that alternatives are inferior.

| Choice | Viable options and observable consequences | Initial recommendation |
| --- | --- | --- |
| C1. Cloud execution substrate | Agent endpoint reuses a mature harness/session but gives the OS less visibility/control. Raw API plus OS loop gives uniform tools/evidence and tighter per-turn limits but adds harness work. | Implement the one actual endpoint you intend to use; declare capability differences. Pick raw+bounded loop if strict uniform tool control is essential. |
| C2. Dispatch integration with LangGraph | Explicit SDK calls in a small adapted graph are easy to audit but require a narrow agent adapter. A custom executor/backend intercepting graph effects reduces agent edits but deepens LangGraph coupling. | Narrow SDK adapter and declared subset. Decide the supported framework/version boundary before implementation. |
| C3. Pressure policy authority | Advisory/manual assignment is predictable and easy to evaluate. Deterministic automatic policy can use idle quota and reduce stalls, but needs eligibility rules, hysteresis and quality evidence. | C4. Reassignment granularity | New-attempt-only rebinding gives clean provenance but repeats setup/work. Safe-point continuation rebinding saves work but needs portable transcripts/tools/state. Native provider-session migration retains more state only within compatible adapters. | Pending rebind + drain/linked attempt first; enable portable continuation rebinding per tested adapter pair. |
| C5. Quota exhaustion policy | Wait preserves subscription spend discipline but extends latency. Paid overflow buys latency at added spend/data exposure. Local downgrade saves cloud capacity only for tasks whose capability floor permits it. | Configure per priority/task class; keep review reserve where possible. No universal fallback. |
| C6. Review cadence | Review each completed process or batch unresolved completions at sprint boundaries; the former spends more cloud quota, the latter can delay dependent work. Every verdict still requires coordinator resolution. | Batch normally; request review at blocked dependency frontier as well as queue exhaustion/issue threshold. | C7. Verification scheduling | FIFO preserves arrival fairness; age-aware priorities can favor dependency-critical work but need bounded overtaking. Lock order remains verification then shell. | FIFO initially; measure shell and verification wait/hold time before adding priority. |
| C8. Documentation freshness | Barrier flush before next sprint gives one consistent doc version but adds latency/cost. Versioned asynchronous flush lets code advance with old docs plus explicit deltas but needs staleness-aware context. | Retain backlog always; permit versioned deltas initially, block only when a task explicitly requires fresh docs. |
| C9. Provisional publication policy | Publishing every completed commit, including fail/uncertain, matches the proposed handoff and enables explicit senior undo but propagates questionable dependencies. Retaining those commits privately limits propagation but changes which work later agents receive. | Publish completed commits provisionally with hazards and unresolved reports; senior review remains authoritative. |
| C10. Local concurrency/residency | One decode and retained model minimizes peak memory/churn. Continuous batching may improve throughput but increases context/KV demands and latency variance. ## 13. Problems still to solve

1. **Concrete hardware and backend fit:** which local model, context/KV settings, RAM/VRAM domains, tool startup peaks and headroom meet the memory envelope? Measure them before setting worker/batching caps.
2. **Quota truth:** what each chosen subscription exposes, how stale readings are, what other account users consume, and whether a useful review reserve is predictable. Percentages do not supply a hard per-job consumption bound.
3. **Agent-endpoint control:** can the chosen Codex/other endpoint enforce the required tools/workspace, return complete enough evidence, interrupt/reconnect reliably, and bound usage? Unsupported capabilities need explicit exclusion or a weaker advertised guarantee.
4. **Portable reassignment:** which state can move local↔cloud without changing task meaning? Define adapter-pair compatibility and a canonical action/observation history; hidden provider reasoning/session internals are unavailable.
5. **Quality/capability floors:** how to mark tasks local-eligible and measure the cost of an upgrade/downgrade. No fixed pressure threshold proves a weaker model can solve the same task.
6. **Review-trigger policy:** set unresolved thresholds, no-progress limits, dependency-frontier triggers, and reserve consumption. Avoid both paid review on every minor error and a blocked queue waiting forever for an empty queue.
7. **Assessment quality:** how many final local loops, which testing/examination prompts and evidence thresholds distinguish successful from uncertain reliably? Reserve an assessment allowance and prevent weak tests or self-edited criteria from producing unjustified success.
8. **Undo blast radius:** identify later tasks, interfaces and effects affected by an agent commit before retaining or reverting it. File overlap alone misses semantic/build dependencies; a Git revert does not prove the rest of the project still works.
9. **Documentation consistency:** select freshness barriers, batch threshold and summary validation; define how code/doc commits relate without a self-triggering update loop.
10. **Steering with a stuck local agent:** the planner waits for the captured running set, not the queue. Define how to surface interruption and request an explicit separate stop/recovery decision when one member cannot finish; do not silently apply steering early.
11. **Cross-store durability and retention:** specify fsync/power-loss target, artifact/checkpoint pruning, orphan collection and restore procedure; persistent libraries alone do not establish a consistent machine snapshot.
12. **Unknown tool completion:** choose the application adapter protocol for confirming a coding/shell operation ended before releasing exclusion. Identify remote effects that Git cannot undo. Host-kernel containment design is outside the project.
13. **Evidence after reconciliation or undo:** decide which examination/tests to repeat after reverting a commit, which later agents become questionable, and when to replan instead of automatically replaying their work.
14. **Future program interface:** determine the exact LangGraph adapter/ABI that lets new programs declare needed capabilities without promising arbitrary drop-in compatibility or building a general graph optimizer first.
